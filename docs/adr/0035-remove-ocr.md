# ADR 0035：撤销 OCR 与翻译

- 状态：已采纳（`feat/remove-ocr`，尚未发布）
- 影响范围：删除 `src/ocr/`、`src/app/bubble/`（OCR 文字气泡）、`src/settings/panel/ocr.rs`、
  `assets/icons/ui/toolbar/ocr.svg`、`CONTEXT.md`；修改 `app`（消息常量与处理器）、`overlay`（`Action::Ocr` / `ocr_key` / `on_ocr`）、
  `render/icon`（`Icon::Ocr` 与光学缩放）、`settings`（`OcrConfig` / `hotkey.ocr_key` / 面板「OCR 翻译」页 / 可见性槽位）、
  `output`（删除仅服务于气泡的 `copy_text_to_clipboard`）、`Cargo.toml`（Windows 特性与 `windows-future`）
- 相关：取代 ADR 0022（本地 OCR + 文字气泡，保留为历史实现记录）、
  ADR 0033（工具栏可见性：元素 24 → 23）、ADR 0028（贴图编辑模式：输出组 3 → 2）、
  PRD §5.2（OCR-1～OCR-13 与翻译条款改为历史追溯）

## 背景

OCR 自 v0.8.1 转正，翻译在 `feat/ocr-cloud-boost` 分支上做到「配置 + 请求 + 气泡第二区域」。
继续往下走只有两条路，都不便宜：

- **提本地精度**：`Windows.Media.Ocr` 的天花板是明确的——小字号、复杂版式、表格、公式都会漏或串行。
  改善只能靠预处理堆料（放大倍率、二值化、行切分），收益递减且会拉高内存与耗时。
- **改走云端 API 传图**：要新增 HTTP 客户端、密钥管理（DPAPI）、隐私授权、超时与重试、成本提示，
  包体与代码量一起涨，还要在「不联网也能用」与「联网更准」之间长期维护两套路径。

两条路都指向同一个结果：**为了一件事把「轻量、常驻 ≈0 开销」的底线让出去**。而需求本身没有终点——
普通 OCR 能用之后，用户会接着要表格识别、数学公式识别、版式还原。

## 决策

OCR 与翻译**整块撤销**，代码删除，不回退为「默认关闭」的可选功能：

- 删 `src/ocr/`（WinRT 引擎、图像转换、行序重排）与 `src/app/bubble/`（原生 `EDIT` 卡片窗口）；
- 删设置面板「OCR 翻译」页（`Section` 7 → 6 页）、`OcrConfig` 与 `[ocr]` 配置段、`hotkey.ocr_key`（键帽行 16 → 15 项）；
- 删工具栏 OCR 按钮与 `T` 键（可见性元素 24 → 23 项、输出组 3 → 2 项）、`Icon::Ocr` 与其图标资源；
- 删只被气泡使用的 `output::copy_text_to_clipboard`；
- `Cargo.toml` 去掉只服务 OCR 的 Windows 特性（`Media_Ocr` / `Storage_Streams` / `Win32_System_WinRT` /
  `Globalization` / `Graphics_Imaging` / `Foundation`），并去掉对 `windows-future` 的**直接**依赖
  （`windows-core` 保留，`render/text` 的 `implement` 宏要用）。`windows-future` 不能从 `Cargo.lock` 里消失：
  `windows` crate 自己无条件依赖它，只是代码里再无使用。

**不做迁移**：`config.toml` 里遗留的 `[ocr]` 段与 `hotkey.ocr_key` 字段被 serde 忽略，不报错、不写回。
用户侧没有替代入口，直接告知用其他软件。

## 理由

1. **与产品定位冲突**。轻截的卖点是「常驻≈0、触发即用」。OCR 要 WinRT 初始化、要全屏位图以外的一份
   引擎侧位图、要后台线程与卡片窗口；云端增强还要再加网络栈与密钥。每一项都在给「轻」做减法。
2. **精度天花板无法用工程手段绕过**。本地引擎的识别率不随投入线性提升；翻译质量又被 OCR 精度直接拖住，
   错字会让译文整体跑偏——「能用但不好用」的功能比没有更消耗信任。
3. **需求会持续膨胀**。表格、公式、版式还原、多语言混排，每一项都是独立工程量，且都不属于截图工具的核心价值。
4. **投入产出不成立**。功能已经开发完成，但实际使用效果不及预期，继续维护的成本远高于它能带来的价值。

## 影响

- 用户侧：`T` 键、工具栏 OCR 按钮、设置页「OCR 翻译」全部消失；README / PRD / 设置面板文案同步。
- 仓库侧：净删约 1500 行 Rust（含测试）、1 个图标资源、1 个**直接**依赖；`cargo test` 336 项绿（`--ignored` 7 项），
  `cargo fmt --check` / `cargo clippy` 无新增告警。
- 已知边界：工具栏宽度回归——移除 OCR 按钮后 1366×768 @ 200% 不再超宽（1332 < 1366），
  超宽用例改到 1280×720 @ 200%；ADR 0033 的已知边界仍在，出路依旧是隐藏元素。
- `CONTEXT.md` 同批删除并加入 `.gitignore`：它在 `3da1fea` 已被删除过一次（内容与 PRD §4 编号表、模块注释重复，
  且无人维护），后来被误加回；三处引用（ADR 0032 / ADR 0033 / `settings/toolbar.rs` 注释）改指现存文档。

## 未采纳方案

- **保留 OCR、默认关闭**：等于把成本留给想用的人（先开开关、等引擎初始化），且代码与依赖照旧在仓库里，
  与「砍掉」的收益差得远；v0.11.0 已经试过「撤掉总开关、靠可见性管按钮」，事实证明那只是把复杂度转移到了设置页。
- **只砍翻译、留本地 OCR**：翻译是唯一让 OCR 结果「有用」的出口，且本地 OCR 的成本（WinRT、卡片窗口、
  行序重排）本来就由 OCR 独占，留一半等于留全部负担。
- **把 OCR 做成插件 / 外置进程**：需要稳定的进程间协议与版本兼容，工程量比功能本身更大。

## 对外说明

> **AirSnip 轻截将撤销 OCR 与翻译功能，如需使用相关功能，请通过其他软件平替。**
>
> 这两个功能与轻截的设计理念不符。为了提升 OCR 精度或实现 API 传图，不可避免地会增加产品体积，
> 而且可能无法完全满足用户需求（例如普通 OCR 可用后，用户又希望支持表格或数学公式识别）。
> 由于 OCR 精度有限，翻译结果也难以保证准确，总体来看，这些功能虽然已经开发完成，
> 但在实际使用中效果可能不尽如人意，且占用了大量开发时间，得不偿失。
