# ADR 0037：窗口吸附（悬停识别整窗矩形，单击选中）

- 状态：已采纳（v0.12 开发期）
- 影响范围：`src/overlay/{mod,opts,wndproc/mod,interaction/mouse,snap/{mod,hit,draw}}.rs`、
  `src/settings/{mod,panel/{controls,controls/layout,draw,interact}}.rs`、`src/app/actions.rs`、
  PRD CAP-6 / §4.7
- 相关：ADR 0023（命中优先级）、ADR 0028（贴图编辑模式）、ADR 0036（默认移动态）、issue #62 / #54

## 背景

论坛反馈（issue #62，同源 #54）要求「窗口捕捉，甚至 UI 元素捕捉」。PRD `CAP-6` 一直是 P1 未实现：
`src/overlay` 只有自由拖拽（`interaction/draft.rs`），配置里也没有对应开关。

issue 把方案分成两级：一级整窗矩形吸附（成本低），二级控件级捕捉（UIA，成本中高且有跨进程阻塞风险）。
本轮只做一级，二级另开 issue 跟踪——本轮零新依赖、零新 `windows` crate feature。

## 决策

1. **交互模型：悬停预览 + 单击选中**。没有选区时光标停在哪个窗口上就高亮那个窗口矩形（不等按下），
   单击把它变成选区、直接进入既有标注流程；从按下就开始拖（超过 `CLICK_SLOP` = 2px）则退回原来的自由框选。
   这是 PRD `CAP-6` 的原文措辞，也是用户对截图工具的既有预期。
2. **只在没有选区时预览**。框好之后（进入移动 / 标注态）悬停不再高亮——那时用户在做标注，
   另一窗口的高亮框是干扰；「按在选区外 = 重新框选」的既有语义因此一个字都不用改。
   贴图编辑模式（ADR 0028）从第一帧就有锁定选区，吸附天然不生效，无需额外分支。
3. **候选框是轻量的**：accent 细边 + **半亮**（原图压暗一档，`CAND_K = DIM_K + (256-DIM_K)/2`）+ 尺寸提示，
   **不画八向手柄、不出工具栏**。预览只是「即将选中」，画上手柄与工具栏会让用户以为已经确认；
   单击后走现有 `set_selection`，暗化、手柄、工具栏都不必重写。
   **不回贴全亮**：候选常常就是整屏（任务栏自动隐藏 + 窗口最大化、全屏窗口），全亮的话暗化一点不剩，
   用户看不出覆盖层已经生效、只会以为 `F1` 没反应（实测反馈）。半亮同时把「预览」与「已确认」在亮度上分开了。
   尺寸提示用与选区同一套避让（`text_rect`）后再**夹回屏幕内**：贴底的整屏候选否则会把提示画到屏幕外。
   **首帧预画**（`prime_snap_at_cursor`）：候选在窗口显示**之前**就画进 `display`（不上屏），
   让 `UpdateWindow` 的那一次全窗上屏就是「暗化 + 半亮候选」。
   否则会先上一帧全暗（首次 `WM_PAINT`）再改成半亮，看起来是「明亮 → 极暗 → 半亮」两步闪烁（实测反馈）。
4. **命中查询走 Z 序枚举**：`GetTopWindow` + `GetWindow(GW_HWNDNEXT)` 自顶向下，第一个「可见、含光标、
   不是本覆盖层窗口」的顶层窗口即目标。
   - 不用 `WindowFromPoint`：覆盖层铺满虚拟屏且置顶，命中的永远是它自己；issue 建议的
     「临时加 `WS_EX_TRANSPARENT` 再查」有一个真实的样式回滚窗口，期间覆盖层对外部鼠标「不存在」，
     而且能否拿到底下窗口依赖系统实现细节而非文档保证。
   - 边界用 `DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)`，**不用** `GetWindowRect`：
     后者含 Win10+ 不可见的缩放边框与阴影，会让选区比视觉窗口大若干像素。DWM 给的是物理像素，
     与「所有坐标统一为物理像素」一致；减去抓屏原点后夹到虚拟屏内。
5. **候选过滤**：跳过不可见、最小化（`IsIconic`）、DWM cloak（`DWMWA_CLOAKED`）、零 / 负尺寸、
   DWM 查询失败（不回退 `GetWindowRect`，宁可这次不吸）、以及桌面壳窗口类 `Progman` / `WorkerW`。
   桌面铺满整屏，不排除的话覆盖层一打开光标不在窗口上就整屏高亮、单击变全屏截图，既吵又抢掉
   「按在空白处重新框选」。任务栏与 AirSnip 自己的贴图窗口**仍是候选**（贴图窗口是独立窗口类，
   用户想截自己贴在屏幕上的图很自然）。
6. **查询时机：每次 `WM_MOUSEMOVE` 先比 hwnd，变了才查 DWM 边界与重绘**。`GetTopWindow` 枚举是微秒级，
   DWM 查询与脏区重绘只在真换窗口时各发生一次。不做时间节流（issue 的 30ms 建议会带来「移过去要等一下才亮」
   的迟滞），也不引入定时器——待机 CPU 0% 的红线禁轮询。
7. **开关是配置项 `window_snap`（bool，默认 `true`）**，设置面板「通用」页新增一行「窗口吸附」，
   立即写回配置、下一次截图生效。默认开是为了让论坛诉求开箱即满足；老用户升级后首次截图行为会变，
   所以「关掉后与当前版本完全一致」是必测项。
8. **长截图不特殊处理**：代码里没有「长截图模式」——长截图视口就是「普通覆盖层里框好选区后按 S」。
   吸附在框选阶段生效后按 S，拿到的就是吸附出来的整窗，正是「整窗滚动截屏」这个最常见需求。

## 备选方案

- **拖动边缘磁吸**（不给单击选整窗）：不改变「按下即框选」的心智模型，但选整窗仍要拖到大概位置，
  论坛诉求只满足一半。
- **只在按住修饰键时吸附**：侵入最小、老用户零惊扰，但功能不可发现；且 `Ctrl` 已被「Ctrl+拖动移动对象」
  占用（ADR 0023），要另选一个键。
- **`WindowFromPoint` + 临时 `WS_EX_TRANSPARENT`**：见决策 4 的理由。
- **排除整个 AirSnip 进程的窗口**（按 PID）：逻辑最简单，但贴图窗口永远吸附不到。
- **再加一个覆盖层内的开关键或硬编码键**：吸附唯一需要「临时关掉」的场景是「这个窗口吸得不准」，
  而那种情况下直接按住拖就是自由框选，退路已存在；快捷键页会多一行、面板行高已经很紧。
- **控件级（UIA）同批交付**：`IUIAutomation::ElementFromPoint` 覆盖面最好（Win32 / WPF / UWP / Chromium），
  但在无响应进程上会阻塞，必须后台线程 + 超时兜底，测试工况（Chromium 树深浅、per-monitor 缩放坐标校正）
  远多于整窗吸附。混在一轮里会把简单可靠的整窗吸附拖住。

## 后果

- 更容易：截一整个窗口不用抠四边；截自己的贴图窗口、任务栏也一样一下点中。
- 更难的代价：**悬停即高亮**意味着覆盖层打开后光标不动也可能出现一个候选框（首帧按当前光标位置查一次），
  首次使用者可能以为已经选好了；「双击窗口」会按「双击空白」的设置动作直接完成截图（单击路径也置
  `down_started_draw`），这是相对今天新增的手感。
- 亮度三档：未选区 = 原图 × `DIM_K`/256（约 53%）、候选 = × `CAND_K`/256（约 76%）、选中 = 原图 100%。
  代价：候选比确认后暗一点，普通窗口上也能看出「这还没确认」。
- 新增状态：`Overlay::snap`（候选矩形 / 候选 hwnd / 按下待定）、`OverlayOpts::window_snap`、
  `Config::window_snap`。
- 已知边界：无边框 / 分层窗口的 DWM 边界与视觉边界可能仍有 1～2px 差；DirectX 独占全屏窗口拿不到有意义的矩形
  （DWM 查询失败 → 直接不吸）；只吸顶层窗口，文档式程序的子面板（如浏览器标签栏）仍是整窗。
