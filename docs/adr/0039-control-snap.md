# ADR 0039：控件级捕捉（UI Automation 下钻）

- 状态：已采纳（v0.12 开发期）
- 影响范围：`src/overlay/uia/{mod,worker,geom}.rs`、`src/overlay/snap/{mod,control,anim,levels,draw}.rs`、
  `src/overlay/{mod,init,opts,wndproc,recapture}*.rs`、`src/overlay/interaction/mouse.rs`、`src/overlay/selection/mod.rs`、
  `src/settings/{mod,panel/*}`、`src/app/{actions,pin_edit}.rs`、`Cargo.toml`（`Win32_UI_Accessibility`）、
  `examples/{uia-probe,uia-hang}.rs`、`docs/uia-probe.md`
- 相关：ADR 0037（窗口吸附）、issue #62（二级）、#54（同源诉求）、PRD `CAP-6`

## 背景

ADR 0037 交付了一级（整窗吸附），本 ADR 交付二级：在同一次截图流程里下钻到窗口内部的子控件
（按钮 / 输入框 / 列表项），不必手动对齐像素。#54 的「Snipaste 式控件识别」由这两级共同覆盖。

方案不是拍脑袋定的：先写了 `examples/uia-probe.rs` 实测（数据与截图见 `docs/uia-probe.md`），
四条门槛（单次 p95 ≤ 30ms、祖先链 5 级累加 ≤ 80ms、窗口级坐标误差 0px、≥5 个程序能拿到子元素）
全部达到或已有确定处理方案后才动手。实测结论里最关键的一条：

> **目标进程无响应时，`ElementFromPointBuildCache` 会阻塞 10 秒**（实测 10023.7ms）。
> 同步查询出局——那等于让覆盖层的鼠标键盘死 10 秒。

## 决策

1. **默认最细粒度 + 滚轮爬层级**：悬停时先显整窗候选（立即可用），UIA 回包到了就换成光标下最深的元素；
   在候选上**滚轮上 = 父级、滚轮下 = 回到更深**，最粗一档永远是整窗。
   **只在预览 + 移动态可爬**：单击确认、选区生成后滚轮回到原有含义（悬停对象调线宽/字号），不会出现
   「选区被滚大了但不知道」。确认后想换粒度就重框一次。
   > 修订（评审）：初稿写的「滚轮在无选区状态原本是空操作，零冲突」只对**移动态**成立——绘制态
   > （用户已按数字键选了工具、但还没框选）滚轮本来就是调线宽 / 字号 / 模糊半径。所以 `climb_snap`
   > 额外要求 `mode.tool().is_none()`，绘制态的滚轮一律让给旧交互。
2. **`control_snap` 独立开关，默认开**：与 `window_snap` 正交（控件级依赖窗口级）。
   关掉后层级止于整窗，行为与 ADR 0037 完全一致。设置面板「通用」页一行，立即写回。
3. **常驻 worker 线程 + 完全异步**：会话开始时起一个线程，`CoInitializeEx(MTA)` + `CoCreateInstance(CUIAutomation)`
   只付一次；请求通道深度 1（覆盖层只留最新一条），回包经 `Arc<Mutex<Option<Reply>>>` + `PostMessage` 唤醒覆盖层。
   **覆盖层 UI 线程永不等待 UIA**，所以 10 秒卡死只会让「控件级」暂时失效，画面与鼠标不受影响。
4. **按窗口熔断**：一次查询耗时 ≥ 1s 就把该窗口拉黑 30 秒，期间只给整窗候选、不再发请求；冷却后允许重试一次。
   熔断粒度是 `hwnd` 而不是 `pid`——挂死的是某个窗口，不该连坐同进程的其他窗口。
5. **不靠全局命中测试，从窗口自己的树向下钻**：`ElementFromHandleBuildCache(目标窗口)` 拿窗口元素，
   再逐层挑「包含光标、面积最小」的子元素，直到没有更小的；这条路径（由深到浅）就是层级链，
   最粗一档永远补上整窗。集成测试实测：记事本 2 层、资源管理器 6 层、任务栏 1 层。
   - **为什么不用 `ElementFromPoint`**（最初的实现）：它做的是全局命中测试，而截图覆盖层铺满屏幕且最上层，
     命中的永远是覆盖层自己（实测日志：`根进程 …(airsnip.overlay)`）——控件级在真实截图里永远是 0 层。
     从窗口元素向下走不依赖全局命中，顺带对任何遮挡物（全屏工具、录屏层）免疫。
   - 节点预算 400、深度上限 12：UIA 树可能很大（Chromium 上千节点），必须能随时停。
6. **坐标口径：窗口级用 DWM 扩展边框，控件级矩形一律裁到该边框内**。实测普通窗口 UIA 与 DWM 完全一致，
   但 UWP 宿主窗口（`ApplicationFrameWindow`）的 DWM 比 UIA/`GetWindowRect` 多 7px；
   以 DWM 为准可以保证「整窗吸附」与控件级之间切换不出现 7px 跳动，代价是贴窗口左边缘的控件最多少 7px。
7. **缓存请求必须是 `AutomationElementMode_Full`**：`None` 模式下元素不保留 underlying element，
   树导航会直接报「无效指针」（实测踩过）。`Full` 下缓存依然有效，一次跨进程往返取回全部属性。
8. **预热**：worker 起来后立刻发一次废查询。实测首次查询要 20–40ms（provider 启动），
   这笔开销放在覆盖层淡入那 120ms 里，不占用户的第一次悬停。
9. **层级链必须允许「只有 1 级」甚至 0 级**：实测存在没有任何子元素的程序（UWP 宿主、自绘编辑器），
   所以最粗一档只能由我们自己的窗口矩形提供，不能依赖 UIA 树本身。
10. **只在没有选区时生效**（与整窗吸附同一条件）；贴图编辑模式选区锁定，天然不启用；长截图不特殊处理。
11. **查询节奏跟光标走、但有节制**：一个在途请求就够（在途时不发新请求）；**光标离开当前候选矩形**
    （= 跨到另一个控件）就立即重查；在候选内部小范围移动不查；内部移动超过 24px 才重查（大元素里也能继续细化）；
    上一查什么都没拿到（0 层）的窗口要用 120px 步长才重试（否则鼠标每挪一点就白查一次）。
    早期版本的「每个窗口只查一次」会让**切换控件完全没反应**，实测手感很僵。
12. **候选框过渡动画**：任一边至少移动 6px 就做 **90ms（15ms × 6 帧，缓出）** 的插值，否则直接跳。
    每帧只重绘「上一帧与这一帧之间」的带状区域，开销远小于一次完整候选重绘。
    过渡中来了新目标就从**当前显示位置**重新起一次（连续、不积压）；
    **按下时立即落到终点**（`Snap::finish_anim`），否则会选中一个中间尺寸的矩形。
    候选在**按下待定期间冻结**：`on_uia_reply` / `climb_snap` 在 `snap.pending.is_some()` 时直接返回。
    否则「松手选中 `pending.rect`」与「画面上的候选」会分叉，且新候选的边框 / 尺寸提示会留在屏上
    （`set_selection` 的脏区只覆盖它自己那一块）。
    回包还要**校验光标**：层级是按请求发出时的点算的，若最深一级已不含当前光标就丢弃（等下一次重查）——
    否则会高亮一块光标不在里面的矩形，按下去还会退化成自由框选。
13. **自绘程序的兵底：客户区**。UIA 一点子元素都没给时（winit 自绘、Qt 自绘、UWP 宿主），
    用 `GetClientRect` + `ClientToScreen` 合成一层「客户区」矩形；与整窗相差 ≤4px（无边框窗口）就不做这一档。
    这样至少能「整窗 ⇄ 客户区」两档切换——截窗口内容不要标题栏与边框是高频需求，而这层不靠 UIA，成本两个 Win32 调用。
    **子窗口枚举（`EnumChildWindows`）暂不做**：实测 winc 0 个子窗口、微信只有 `MMUIRenderSubWindowHW`（= 内容区本身），
    对这两个主流程序没额外收益，不值得多一套与 UIA 混搭的层级逻辑。
    **也不会做图像识别/OCR 猜控件**：那是「猜」不是「识别」，误吸附概率高，且与 ADR 0035 撤掉 OCR 的取向相背。

14. **亮度分三档：桌面暗 < 窗口半亮 < 控件全亮**（评审后修）。ADR 0037 的「候选区半亮」是在只有整窗一档时
    成立的：一旦下钻到控件，候选矩形比窗口小，而候选之外一律是暗图，**同一个窗口的标题栏 / 工具栏 / 状态栏
    就落回暗图**——实测（记事本）就是「顶部多了一条暗带」，窗口内出现一半亮一半暗的断层。
    现在渲染按**两级矩形**给亮度：窗口矩形回贴原图后再压暗一档（`CAND_K`，与 ADR 0037 一致），
    控件矩形直接回贴原图（全亮）；桌面上不属于任何候选的部分仍是暗图。
    - 为什么不用「整窗半亮 + 控件只描边」：最大化窗口下整屏都是半亮，控件只剩一条细边，看不出「只截这一块」。
    - 为什么控件不也保持半亮（两档）：那就是本项要修的断层。
    - **整窗一档必须仍然是半亮**（`Snap::is_finer_than_window` 守门）：全屏窗口下全亮等于覆盖层没生效。
    - 脏区跟着变大：换窗口时旧窗口整块要从半亮改回暗（`Snap::prev_window` → `repaint_snap` 的 `windows` 参数），
      确认选区 / 清空候选时旧窗口同样要重绘（所以 `Snap::clear` 返回 `(旧候选, 旧窗口)`）。
      窗口没变时（纯控件级 / 动画帧）不带窗口矩形，否则每次回包都要重绘整个窗口，60 FPS 红线不保。

## 备选方案

- **`ElementFromPoint` + 沿祖先链上溯**（最初的实现）：思路最直接，但有致命问题——覆盖层自己就在最上层，
  全局命中永远命中它，真实截图里层级恒为 0（靠调试日志才发现，设计阶段看不出来）。
- **把覆盖层临时改成 `WS_EX_TRANSPARENT` 再查**：能绕过覆盖层，但样式翻转期间覆盖层收不到鼠标消息，
  且与 worker 线程存在竞态。
- **同步查询 + 超时**：实测会卡 10 秒，直接否掉。
- **每次查询临时起线程**：无状态，但每次 `CoInitialize` + `CoCreateInstance` + 建缓存请求要几到几十毫秒，
  鼠标快速划过时根本跟不上。
- **`AutomationElementMode_None`（只用缓存、不保留引用）**：本来能再省一次往返，但树导航直接报「无效指针」。
- **按 pid 熔断 / 全局熔断**：浏览器开 20 个窗口时一个页面卡死就毁掉全部控件级，太粗。
- **默认整窗、按键才下钻**：论坛诉求就是「不用滑动鼠标」，默认整窗等于每次多一步。
- **不裁到窗口内**：Chromium 常给出比窗口还大的元素（整页滚动区 `2514×3992 @42,-960`），
  不裁就会选出一个比屏幕还高的矩形。

## 后果

- 更容易：鼠标一停就有一个细到控件的候选；滚轮一滚就能在「控件 / 面板 / 整窗」之间切换；
  卡死程序不再拖垮截图（自动退化为整窗）。
- 更难的代价：
  - 无响应的目标（`Ghost` 窗口）与 UIA 不暴露子元素的程序（部分自绘界面）永远只有整窗；
  - 首次悬停可能先看到整窗、几十毫秒后才「收紧」到控件，有轻微切换感（这是异步的必然代价，换来的是永不卡顿）；
  - 真的很卡的目标会让 worker 线程一直卡着（无法安全终止 COM 调用），会话结束后该线程泄漏到它自己醒来为止；
  - UWP 窗口贴左边缘的控件最多少 7px；
  - `windows` crate 多开 `Win32_UI_Accessibility` 特性（无新第三方依赖；发布包体积由链接器裁掉未用代码）。
- 新增状态：`Overlay::{control_snap, uia}`、`snap::Snap::{window, levels, level}`、
  `uia::Uia::{worker, pending, blocked, next_gen}`、`Config::control_snap`、`WM_SNAP_RESULT`。
