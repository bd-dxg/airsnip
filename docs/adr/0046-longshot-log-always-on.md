# 46. 长截图日志常开（SYS-9）—— 不加开关，出问题时日志就在

- 状态：已采纳（v0.14.0 之前）
- 影响范围：`src/longshot/{debug,engine}.rs`（开关 / 目录 / 轮转 / 帧抽样分级）、
  `src/settings/panel/{controls,controls/sections,link,interact}.rs`（一行按钮）、`src/diagnose/text.rs`
- 相关：issue #200、#196 / #129 / #157（驱动它的排障场景）、ADR 0044（长截图拼接埋点）、ADR 0041（面板几何）

## 背景

长截图出问题（#196 / #129 / #157）时唯一能定位的手段是看日志与帧：`longshot/debug.rs`
在 `AIRSNIP_DEBUG=1` 下把每步状态写进日志、把可疑帧对落成 PNG。但这套流程要求用户退出托盘、
开 PowerShell、`cd` 到安装目录、设环境变量再启动——**报问题的用户不是开发者**，
七步图文教程之后多数人还是会放弃，我们只能靠「你能不能再说得具体点」猜问题。

## 决策

### 1. 日志**常开**，不设开关

第一版按 issue 的建议做过「设置面板一个诊断日志开关 + 打开日志文件夹」（`[diagnostics] debug`、
`AtomicBool` + 环境变量取或）。复核后**否掉开关**，理由：

- 开关的唯一作用是「用户事先知道要开」。issue 的痛点是用户不是开发者，
  开关只是把失败模式从「不会设环境变量」换成「没开开关」——我们依然要在 issue 里说
  「你先打开诊断日志再复现一次」。
- 常开的真实代价很小（逐项核对过）：

  | 项 | 事实 |
  |---|---|
  | 待机开销 | `log()` / `dump_pair()` 的调用点全在 `longshot/{engine,session}.rs`，**只有长截图会话期间才写** |
  | 每次会话体积 | 状态文本每拍一行（实测一次会话 35 段 / 346 次 push），几十 KB |
  | 长期增长 | 4MB 轮转封顶（见决策 3） |
  | 性能 | 拼接路径上多一次 `format!` + 缓冲写，长截图本身的采集/拼接开销远大于此 |

- 唯一的实质代价是**画面**（帧 PNG）可能落盘，而纯文本日志里只有 `hash=` / `offset=` / 得分，
  不含页面内容。这一条用「异常时落盘 + 上限 6 对 + 标签上写明可删」处理（决策 2、4），
  比让用户去猜一个开关更有意义。

于是「用户零操作、出问题时日志一定在」成立；普通用户唯一要做的动作是点一下
**打开日志文件夹**把文件发过来。

### 2. 文本常开，高成本帧抽样留在环境变量下

`AIRSNIP_DEBUG` 从「开关」降级为「更详细的采样台阶」（`debug::verbose()`）：

- **文本日志**（每拍一行 `push: offset=… info=… changed=…%`）常开。`changed_ratio` 同时是
  「画面变了却判没动」的判据，本来就得每拍算，O(行数) 比较、微秒级。
- **异常帧落盘**常开：`still-but-changed`（画面在变却判无位移）与定位失败时落一对 PNG，
  进程内上限 6 对。这是真正能定位 #196 这类问题的素材，必须默认就有。
- **每 25 拍的时间序列抽样**（`seq`）只在 `verbose()` 下做：4K 全屏 PNG 编码几十毫秒一张，
  每 25 拍一次会被感知为卡顿，而它服务的是「开发者人眼看时间序列」，不是普通用户报问题的必需品。

### 3. 日志目录 `%TEMP%\airsnip\`，4MB 轮转

原来日志直接落 `%TEMP%` 根目录。那个目录在任何机器上都有几百个文件，「打开日志文件夹」
等于把用户丢进噪音里。改为 `%TEMP%\airsnip\`（`debug::log_dir()`，调用即 `create_dir_all`），
日志与 PNG 都在里面。

体积：写入时累计已写字节（首次打开从文件现有大小起算，上一次运行留下的也算），
超过 4MB 就把日志改名成 `.log.1`（覆盖更旧的一份）并重开。不引入定时器、不新增线程，
判定在写入路径上，最坏情况多一次 `rename`。
`scripts/` 里只有 `perf-capture.ps1`（`airsnip-perf.log`）与 `gen-third-party.ps1`
（`airsnip-meta.json`）用 `%TEMP%` 根目录，文件名不冲突、不受影响。

### 4. 面板只留一行按钮

「通用」页底部一行：标签 `长截图日志（不含密码，可删）` + 按钮 `打开日志文件夹`
（复用 `output::quick::open_folder`；目录由 `log_dir()` 保证存在，不需要「目录不存在」的分支）。

标签同时承担说明职责：范围（只有长截图）、隐私（不含密码）、可清理（可删）。
两件事合成一行，比「开关 + 按钮 + 说明」三行省地方，也少一个用户不会点的控件。

位置选「通用」而不是 issue 建议的「关于」页：关于页 `40 + 5×46 + QR_ROW_H(200) = 470`，
距固定高 `H = 520` 只剩 50px，加一行按钮还有 4px 余量但二维码块会贴底；通用页 362 → 408
余量充足（ADR 0041 的固定高不变）。

### 5. 反馈文本写日志路径，不写开关状态

「我要反馈」复制文本的开关行末项为 `长截图日志 %TEMP%\airsnip`——比「诊断日志 开/关」
更有用：直接告诉我们去哪拿文件。**写字面 `%TEMP%` 而不是展开后的真实路径**：
后者含用户名（`C:\Users\<名字>\AppData\Local\Temp\airsnip`），而这份文本刻意不带用户目录
（`report_is_compact_and_private` 守门）。

## 未采纳方案

- **诊断日志开关**（第一版实现，已回退）：见决策 1。开着它等于承认「用户得先知道」，
  而这正是要消除的东西。
- **默认开 + 保留开关**：零操作的目标达成了，但多一行 UI + 一个配置项，
  且「我不想要日志」的人可以手动去 `%TEMP%` 删文件——为一个几乎无感的写入加开关不值。
- **文本常开、画面快照受开关控制**：看起来最「稳」，实际把最需要的素材（异常帧）
  压回了「用户先去开开关」的老问题；且多一个配置项 + 面板控件。
- **给普通截图 / 保存 / 贴图也加同类埋点**：那几条链路短，出问题基本能从现象定位，
  凭空加埋点是投机代码（issue 的待确认项也是这个倾向）。
- **把 `debug` 模块从 `longshot/` 挪到顶层 `diagnostics/`**：只有一个消费者，
  挪模块只是换个名字；将来真给别的链路加埋点再搬（`pub(crate) mod debug` 已对外可见）。

## 影响

- **无新增配置项**（`[diagnostics]` 段与开关一并回退）。
- 设置面板「通用」页 7 → 8 行（362 → 408），面板固定高 520 不变；
  `panel_stays_landscape_for_every_section` 与 `each_section_has_its_rows` 守门。
- 行为变化（对普通用户）：长截图会话现在总会写日志；画面快照在异常时刻自动落盘
  （上限 6 对/进程）。`AIRSNIP_DEBUG=1` 仍可用于每 25 拍的时间序列抽样。
- 「我要反馈」文本第三行末项 `长截图日志 %TEMP%\airsnip`（三行结构不变，
  `render_is_three_lines` 守门）。
- **测试隔离**：`debug::enabled()` 生产恒真、`cfg!(test)` 下恒假。拼接用例的模拟帧源
  几毫秒就能跑几十拍，不关会把真实用户的日志写成一团噪音（实测混过 258 行测试日志，
  还丢下一对 164B / 1469B 的失败帧 PNG，用户看到会以为程序坏了），
  也会让「打开日志文件夹」这个功能自己显得像 bug。
- 测试：日志目录是 `%TEMP%\airsnip` 且被创建、轮转让位并覆盖 `.1`、首开从现有大小起算、
  `verbose()` 跟随 `AIRSNIP_DEBUG`、按钮文案不被更新状态盖掉、反馈文本带日志路径且不含用户目录、
  通用页标签不压控件、离屏渲染该行有墨。
